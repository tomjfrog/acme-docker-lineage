A Golden Image is an approved, versioned base that a platform or security team builds once and everyone else is supposed to start from. For containers that usually means a hardened OS (e.g., Chainguard) or runtime image: patched, CIS-baselined, non-root, minimal packages, with required agents baked in, and published to a known catalog or Artifactory repository instead of ubuntu or python from Docker Hub. Application Dockerfiles are meant to FROM that catalog image. The Golden Image team owns the base; app teams own what they add. Building on a non-Golden public image instead is a governance violation and needs to queryable for reporting and governance.  Scouring Version Control-based Dockerfiles is inefficient, error prone and presents lot of room to miss non-compliant images.

That contract breaks as soon as teams rename, retag, or rebuild from an intermediate. Artifactory still holds the image, but not a durable FROM. Name and tag prove nothing. It's possible existing images were published with no Build Info or Evidence, so security cannot tell a blessed base from a public one. The real question is no longer: “did they type the golden path in a Dockerfile?” It is: “does this artifact still root in the hardened catalog?”

The fix going forward is digest-pinned CI that always publishes Build Info and signed lineage Evidence, with AppTrust gates blocking promote unless that proof is present. Layer matching can inventory what is already stored; Evidence is the system of record; AppTrust is how you enforce it.

Evidence is the signed lineage record attached at publish: this digest was built from that base digest, and (when CI records it) the root is a Golden Image. AppTrust consumes those records at promote. If derived-from-golden Evidence is present, the version can move; if it is missing—or only names an intermediate with no walk back to golden—the gate blocks. Evidence is the proof. AppTrust is the enforcement.
